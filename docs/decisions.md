- 2026-10-12: `pyType` became a string ("int", "list[int]", "tuple[int, str]") so container types compare with `==` and need no table. A list is `*runtime.List[T]`, because Python lists alias; a tuple is the runtime's `TupleN[...]` struct, for 1 to 6 elements. Larger tuples, `tuple[int, ...]` and `tuple[()]` are rejected.
- 2026-10-12: List and tuple literals take their type from their elements. `[]` has none, so it needs a type from context (an annotation, a parameter, a return type, or the other operand of `==`, `+`, `in`). Elsewhere it is rejected. Mixed element types, including `[1, 2.5]`, are rejected, since a Go slice has one type.
- 2026-10-12: Aliasing follows Python. Assignment and argument passing share the list; `xs[:]`, `xs.copy()`, `xs + ys` and `xs * n` build new ones. `xs += ys` and `xs *= n` change the list in place (`Extend`, `RepeatInPlace`), as in Python, so aliases see them. `[[0]] * 3` repeats the same inner list, as in Python.
- 2026-10-12: Equality is element-wise, and ordering is lexicographic, both through `runtime.Eq`/`Lt`/`Le`/`Gt`/`Ge`. Both sides must have the same static type. List and tuple do not compare with each other, and neither do `int` and `str`.
- 2026-10-12: Tuples are indexed with an integer literal only, because every position can have its own type. Negative literals count from the end and are checked at compile time.
- 2026-10-12: Unpacking (`a, b = ...`, `for a, b in ...`) declares names that do not exist yet, taking the type from the tuple. There is no syntax to annotate them, so this differs from plain `x = 5`, which is still rejected. A tuple with the wrong arity is a compile error; a list is checked at run time (`ValueError: too many values to unpack`). `a, b = b, a` is a Go parallel assignment when every target is an existing name; anything else goes through temporaries, evaluating the whole right side first. `_` discards.
- 2026-10-12: `for` over a list reads `Len()` and `Get(i)` on every step, so appending while iterating behaves as in Python, and removing makes the loop skip. A string iterates over a list of its characters, built once. `enumerate(x)`, `enumerate(x, start)` and `zip(a, b, ...)` (up to 6 sequences) are accepted only as the iterable of a `for`, or `enumerate(zip(...))`. `enumerate`/`zip` elsewhere and any other iterable are rejected.
- 2026-10-12: Strings are Go strings, so every operation that counts or indexes (`len`, `[]`, slices, `find`) goes through the runtime and decodes UTF-8: O(n) per call. `len("héllo")` is 5. Comparison stays byte-wise, which orders the same as Python's code points.
- 2026-10-12: Slices follow CPython's index normalisation (`runtime.Bounds`). A zero step raises `ValueError: slice step cannot be zero`. Slicing a tuple is rejected.
- 2026-10-12: Method calls dispatch on the static type of the receiver. str: `upper lower strip split join replace find startswith endswith count`. list: `append pop insert extend reverse sort index count remove clear copy`. `split` takes 0 or 1 argument, `strip` 0 or 1, and no method takes keyword arguments except `sort(reverse=...)`. `key=` functions are unsupported because function values do not exist yet.
- 2026-10-12: `upper` and `lower` use Go's simple case mapping. CPython uses full case mapping, so `"ß".upper()` gives "SS" there and "ß" here; this is a known limit.
- 2026-10-12: Beyond the roadmap: `sum`, `sorted(reverse=)`, `repr`, `list.copy/clear/remove`, and `in`/`not in` for str, list and tuple. Without a key function, sort stability only shows with values that compare equal but print differently, such as 0.0 and -0.0; `sort_stability` covers that, including `reverse=True`, which CPython implements by reversing, sorting and reversing again.
- 2026-10-12: `sum()` uses CPython 3.12's compensated summation for floats, so `sum([0.1] * 10)` is 1.0, not 0.9999999999999999. `sum` of an empty `list[float]` is 0.0 here, but the int 0 in Python; that divergence is documented, not fixed. `sum(xs, start)` is rejected.
- 2026-10-12: `min`/`max` need arguments of one type from int, float, str (or one list of them). Python returns the winning object, so `max(3, 2.5)` is the int 3, and a typed result cannot be both. They use Python's tie rule: the first of equal items wins, and a NaN never replaces the best.
- 2026-10-12: Conversions: `int(float)` truncates, `int(str)` parses base 10 with Python's whitespace and underscore rules, `float(str)` accepts Python's grammar only (Go's parser also takes hex floats), and `round(x)` rounds half to even. `round(x, n)` is rejected. A result outside int64 raises OverflowError, which is the int64 limit surfacing, not a Python error.
- 2026-10-12: `**` on two ints needs a literal exponent: non-negative gives an int (`PowInt`, wrapping like all int arithmetic), negative gives a float. A variable exponent is rejected because the result type would depend on its sign. Any float operand gives a float. `PowFloat` raises ZeroDivisionError for `0.0 ** -1` and OverflowError where C's pow returns Inf. A negative base with a fractional exponent is a complex number in Python, which has no equivalent here, so it raises ValueError. Superseded in phase 10: a variable exponent is allowed and the result of an int power is exact.
- 2026-10-12: `divmod` returns a `tuple[int, int]` or `tuple[float, float]`. Dividing by zero uses CPython's messages ("integer division or modulo by zero", "float divmod()").
- 2026-10-12: f-strings become string concatenation with a runtime call per field, chosen by static type. Supported specs: `[[fill]align][sign][0][width][,][.precision]` with type `d`, `f` or `s`, and `!r`/`!s`. `d` needs an int, `s` a str, and an int may use `f`. A float with a precision needs the `f` type. Specs on bool, list or tuple, `!a`, nested `{width}` fields, and `0` together with `,` are rejected. Specs are validated at compile time with the same parser the runtime uses.
- 2026-10-12: `print` accepts `sep=` and `end=` (str only). Any other keyword is rejected, and so are keywords on every other call. `repr` of a str follows CPython's quote choice and escapes, and a one-element tuple prints as `(1,)`.
- 2026-10-12: A user-defined function or a local variable hides a builtin of the same name, as in Python. Generated code avoids Go's own `len`, so a Python variable named `len` or `max` is fine.
- 2026-10-12: An expression statement whose value is not None is emitted as `_ = ...`, since Go accepts only calls as statements and several builtins compile to conversions.

- 2026-10-12: `runtime.PyError` is now a class name plus the constructor arguments. `str(e)` follows CPython: no arguments gives `''`, one gives that argument's `str`, several give the tuple of arguments, and `KeyError` shows the repr of its key. `repr(e)` is `ValueError('x', 2)`. Every error that phases 2 and 3 raise keeps its message and class.
- 2026-10-12: The class table (`runtime/errors.go`) lists BaseException, Exception, ArithmeticError, ZeroDivisionError, OverflowError, FloatingPointError, LookupError, IndexError, KeyError, ValueError, UnicodeError, TypeError, AssertionError, AttributeError, EOFError, ImportError, MemoryError, NameError, UnboundLocalError, OSError, StopIteration, RuntimeError, NotImplementedError and RecursionError, with CPython's parents. SystemExit and KeyboardInterrupt are left out, since nothing here can raise them usefully.
- 2026-10-12: An uncaught exception ends the program like CPython: the generated `main` defers `runtime.Report`, which prints `Traceback (most recent call last):` and `Type: message` to stderr and exits with status 1. Frames are not recorded, so the traceback has no `File` lines; only the last line matches CPython. The deferred call is emitted only when the program uses the runtime, since nothing else can raise.
- 2026-10-12: The harness builds each program and runs the binary, instead of `go run`, so it sees the real stderr and exit status. A case with `expected.err` must exit with status 1 and end its stderr with that line. Every other case must exit 0. This replaces the earlier "stderr contains the message" check.
- 2026-10-12: The name bound by `except ... as e` has the type `exception`. It can be printed, converted with `str()` and `repr()`, used in an f-string field, raised again, and asked for `type(e).__name__`. It cannot be annotated, stored in a list or tuple, compared, passed to a function, returned or given to another exception, so it never outlives its handler. `e.args` and other attributes are unsupported.
- 2026-10-12: Accepted `raise` forms are `raise Cls`, `raise Cls(args...)` with any value type as an argument, `raise e`, and a bare `raise` inside a handler. A bare `raise` outside any handler is rejected at compile time, including inside a function that a handler calls, where Python would raise `RuntimeError`. `raise X from Y` is accepted and `Y` is checked but dropped, because the cause only appears in the traceback. Raising anything else is rejected.
- 2026-10-12: `assert test, message` raises `AssertionError(message)`, evaluating the message only on failure. The test uses Python truthiness, like `if`.
- 2026-10-12: Go has no exceptions, so a `try` body runs in a closure under `runtime.Catch`, which turns a panic of a Python exception into a value. Handlers run in order, and the first whose class list matches wins, using the hierarchy. An exception nobody matches is raised again. A panic that is not a Python exception is a bug and passes through. Handlers run outside the closure, so `break`, `continue` and `return` inside them work as plain Go statements, and an error in a handler propagates.
- 2026-10-12: `break`, `continue` and `return` inside a closure cannot act on the loop or function around it, so they set a status variable (and a result variable for `return`) and return from the closure. The code after the closure reads the status and does the jump, which may itself be inside another closure. A loop inside the closure still uses native jumps. Status checks are emitted only for the jumps that actually occur.
- 2026-10-12: `else` runs when the body raised nothing and made no jump. `finally` wraps the whole try/except in one more closure, runs inline afterwards, and then re-raises what was pending or performs the pending jump. A `return`, `break` or `continue` inside `finally` runs before either, so it replaces them, as in Python. A return value is computed before `finally` runs.
- 2026-10-12: Annotated declarations at the top level of a `try` body are hoisted out of the closure, so the pattern `n: int = int(s)` in the body and `n = 0` in the handler works, and `n` is visible afterwards. If the exception happens before the declaration, Python's `n` is unbound and the Go variable is zero; only a program that reads it would notice. Declarations deeper in the body, in a handler or in an `else`, stay block scoped as in phase 2.
- 2026-10-12: `except:` must be the last clause. A class in an `except` or `raise` that is not built in is "unknown exception class", which is the message for a user-defined class. Handler names go through the same reserved-name check as other variables.
- 2026-10-12: The recursion limit is modelled. A function that can reach itself through calls, found from the call graph after all bodies are generated, starts with `runtime.Enter()` and `defer runtime.Leave()`. The 1000th nested call raises `RecursionError: maximum recursion depth exceeded`; CPython reaches depth 999 in plain recursion, and so does this. Only functions in a cycle count, so frames of ordinary callers above them are not counted, and a program that recurses through ordinary frames only is not guarded. Other functions get no guard and pay nothing.

A generator of random programs mixing `try`, `except`, `else`, `finally`, loops, `break`, `continue` and `return` was run against CPython while this was built, and its output matched. That generator is not kept in the repository.

- 2026-10-12: Phase 5 starts. Scope is `dict`, `set`, comprehensions, generator expressions, `range` as a value, and module variables visible to functions. Everything stays typed. `tuple(x)` waits for phase 6, because its type needs variable-length tuples.
- 2026-10-12: `dict[K, V]` is `*runtime.Dict[K, V]`, a pointer type so aliasing works like lists. Entries live in a slice with a map from key to position, so insertion order survives deletes and re-inserts the way CPython's compact dict does: a deleted key that comes back goes last, and a repeated key in a display keeps its first place and takes the last value. Deleted entries are squeezed out once they outnumber the live ones. A missing key raises `KeyError` carrying the key, so `str(e)` shows its repr.
- 2026-10-12: Keys and set elements are `int`, `str`, `bool`, or tuples of those. Each dict has one key type, so `1 == True` cannot collide inside it. `float` keys and mixed numeric keys wait for phase 10. A list, set or dict as a key is rejected at compile time, where Python raises TypeError.
- 2026-10-12: `d.keys()`, `d.values()` and `d.items()` have their own types (`dict_keys[K, V]` and so on). They are live views. There is no annotation for them, so a view can be used directly (`for`, `len`, `in`, `list`, `sorted`, `sum`, printing, and `&`, `|`, `-`, `^` on keys) but not stored in a variable. A keys view compares equal to a set with the same items.
- 2026-10-12: Changing a dict while iterating it raises `RuntimeError: dictionary changed size during iteration`, or "dictionary keys changed during iteration" when the size is the same but the keys moved, as in CPython. Assigning to existing keys is fine.
- 2026-10-12: `d.get(k)` and `d.setdefault(k)` with one argument are rejected, because they involve `None`, which has no type until phase 8. The two-argument forms work. `dict.fromkeys(keys, value)` needs the value for the same reason. `dict()`, `set()` and `list()` with no arguments take their type from the context, like `{}` and `[]`.
- 2026-10-12: `runtime.Set` is a port of CPython's open-addressing table (`setobject.c`), not a Go map, because the order a set iterates in is its table order and programs print sets. It follows CPython's probing (10 linear probes, then the perturbed jump), resize rule, dummy entries, `pop` finger and the algorithms behind each operator and method (union copies then merges, intersection walks the smaller set, difference may copy first, `difference_update` rebuilds the table when a quarter of it is dummies). Two details were not obvious from the algorithms and were found by comparing against CPython: a new key reuses the last dummy slot on its probe path, and swapping bodies in `&=` leaves each set's finger alone. `runtime/testdata/set_orders.json` holds 250 random operation sequences recorded from CPython 3.13, and a further 7,000 were compared while this was written.
- 2026-10-12: A set display of three or more constants is built the way CPython builds it: a frozenset from the items, rebuilt from that frozenset's iteration order, merged into an empty set. That layout differs from adding the items one by one, and `{100, 8, 16, 24, 32, 0}` prints differently without it.
- 2026-10-12: `hash()` follows CPython: ints modulo 2**61 - 1 with -1 mapped to -2, bool as 0 and 1, tuples by the xxHash-based algorithm, and `str` by SipHash-1-3 over the string in CPython's internal width (one, two or four bytes per character). `PYTHONHASHSEED` is honoured, including CPython's generator for seeds other than 0. With no seed the key is random, so sets of strings iterate in a different order on each run, as in CPython. Tests sort string sets.
- 2026-10-12: The ordering operators on sets mean subset and proper subset. Dicts, ranges and views compare for equality only. Different container types do not compare.
- 2026-10-12: `range(...)` is a value of type `range`: `len`, indexing (negative included), `in` computed without walking, equality by content, `reversed`, and printing as `range(0, 5)`. A zero step raises `ValueError` when the range is built. A `for` loop over a literal `range(...)` keeps its counter loop. `reversed(range)` returns a range, which prints differently from CPython's `range_iterator`.
- 2026-10-12: Lazy things have the type `iter[T]`: generator expressions, `zip()`, `enumerate()` and `reversed()` of a list, str or dict. An iterator is one-shot, cannot be indexed, measured, searched, stored in a list or annotated, but can be looped over and given to `list`, `set`, `dict`, `sum`, `min`, `max`, `sorted`, `any`, `all` and `str.join`. `reversed(list)` reads the list live and stops if it shrinks; `reversed(set)` is rejected as in Python.
- 2026-10-12: Every `for` loop now runs a cursor (`Next` and `Value`) instead of counting indexes, which gives one way to loop over lists, strings, dicts, sets, ranges, views and iterators. Lists are still read live, and dicts and sets check for changes. `for i, x in enumerate(xs)` receives tuple values from a lazy `enumerate`.
- 2026-10-12: A list, set or dict comprehension compiles to an immediately called function literal that holds the loops. Its variables are local to it, so they shadow outer names and do not leak. A generator expression compiles to a small state machine with a cursor per `for` clause, so it produces one item per call: `any(check(x) for x in xs)` stops calling `check` at the first true result, and a `for` loop over a generator interleaves the producer's side effects with the body. The outermost iterable is evaluated when the generator is created, as in Python.
- 2026-10-12: Functions that consume a whole iterable (`sum`, `min`, `max`, `sorted`, `list`, `set`, `dict`, `str.join`) collect it into a list first. That is equivalent to Python unless the consumer has side effects between items. `any` and `all` take the iterable as it is, which keeps their short circuit.
- 2026-10-12: Unpacking works on any iterable. A str, dict, set, range or view is first turned into a list, and the count is checked at run time like a list.
- 2026-10-12: Module-level variables are package-level Go variables, so functions can read them, and rebind them after `global`. A function with defaults, keyword-only parameters or `*args` can still be stored in a Callable of fewer parameters: the compiler wraps it in an adapter that supplies the defaults. A Python loop variable is one variable for the whole loop, and the generated code keeps it that way, so every closure made in the loop sees its last value.

- 2026-10-12: A decorator must have the exact type `Callable[[F], G]` where `F` is the type of the function it decorates. Decorators stack bottom to top and may take arguments (`@repeat(3)`). Reading these attributes on a Callable value is rejected, since the name is gone. A bare string or `...` statement does nothing and is allowed anywhere.

- 2026-10-12: A class is a Go interface of the same name, which is the static type of every variable holding an instance, plus one struct per class (`_pyc_Name`) implementing it. The interface lists the accessors (`Get_x`, `Set_x`), the methods (`M_name`) and a marker (`Is_Name`) for each class in the MRO. A value of a subclass is accepted where a base class is expected, because Go interfaces are satisfied structurally and the markers make `isinstance` nominal. The upcast is done by relabelling in `exprAs` and `coerce`, so lists of a base class can hold subclass instances. Instances are pointers, so aliasing works as in Python, and every struct has a dummy byte because Go may give all pointers to zero-sized values one address.
- 2026-10-12: Each method is compiled once per class that inherits it, with `self` bound to that exact class (`M_f__Definer` on `_pyc_Exact`). The interface method `M_f` forwards to the definer the MRO picks. The price is code size, and that a base class method is compiled for every subclass. `@classmethod` is a Go function per exact class, `@staticmethod` a plain function, and both are also listed in the interface so an instance can call them.
- 2026-10-12: Instance attributes come from their first assignment in a method, not from annotations alone. Before code generation, every method is compiled once with its output thrown away and `self.x = v` declares `x` with the type of `v`; this repeats until no attribute is new, since a method can read the attributes of a class defined later. A class-body annotation (`x: int`) also declares one. An attribute that no method assigns is rejected at its use, and one that is read before it is assigned reads the Go zero value where Python raises `AttributeError`. Reading an attribute that only subclasses define, from a base class method, compiles to a run-time `AttributeError`.
- 2026-10-12: A class attribute is a package variable (`_pyca_Class_x`) set where the class statement stands. The scan for attribute names that some code assigns is by name over the whole module, so a class attribute whose name is assigned through any instance gets the flag. `C.x = v` assigns the class attribute, but only on the class that defines it; assigning an inherited one through a subclass would create a new attribute and is rejected.
- 2026-10-12: Overrides must have the signature of what they override, since the Go interfaces have to fit. A property overrides a property or an attribute of the same type. These checks reject programs that Python accepts, and mypy would flag most of them.

- 2026-10-12: A class that defines `__eq__` without `__hash__` is unhashable, `hash()` of it raises `TypeError: unhashable type: 'A'` when it runs, and the default hash is by identity. Instances are dict keys and set elements only when the class hashes by identity: the maps are Go maps and cannot call `__eq__` or `__hash__`. A class with its own `__eq__` or `__hash__` as a key is rejected until phase 9. `hash()` of floats follows CPython's algorithm, so a float field in a frozen dataclass hashes like Python.

- 2026-10-13: The GIL is a queue of tickets.
